## 二、复验方法（为什么这次的结论可以信）

### 1. 用"修好会自动变绿"的机制，而不是靠人去对账

上一轮我提交 43 条时，其中 20 条已经预写了**可证伪的 `xfail` 用例**。它们的判据是：
**修好即 XPASS**。所以这一轮不需要开发会话逐条告知"我修好了"——

```
30 条 xfail 用例 → 全部转为 XPASS（0 条仍 xfail）
```

这 30 条覆盖 **20 个 issue**：`#4 #5 #6 #9 #10 #11 #12 #13 #14 #15 #17 #31 #34 #35 #42 #48 #49 #50 #51 #53`。
逐条比对后确认：**没有一个"修好了但标记还挂着"的（0 xpassed 之外的残留），也没有一个"红着但被 xfail 掩盖"的**。

### 2. 摘掉标记 —— 这一步不是收尾，是**恢复守卫**

`xfail(strict=False)` 的语义是"失败也算通过"。也就是说：**标记留着，回归时套件依然是绿的**。
所以修好之后必须摘标记，否则那 25 条守卫等于**死了**（看着在、实际不拦）。

已用脚本摘除 25 处（脚本先 dry-run 打印每一处的 `reason`，确认形状一致后才写入），
摘完 `pytest tests/verify` → **312 passed, 0 failed**：30 条现在都是硬断言。

### 用户可见的后果（实测，不是推理）

同一岗位、同一简历，只改 `variant`：

```
第 1 次 variant=with_project    → source=llm，返回「…Python 与 FastAPI…方便请教一下这个岗位目前最看重哪一块？」
第 2 次 variant=without_project → source=llm，返回的**还是上面那段**
   模型这次被要求给的是：「…Python 与 RAG…想请教一下这个岗位现在最缺的是哪一块能力？」
   g2.full == 回复A → True ；g2.full == 回复B → False

```

**关键点是 `source` 仍然是 `llm`** —— 用户看到的是"刚生成的"，实际拿到的是上一版的文案。
`jh today --variant` 这类 A/B 用法会直接给出与所选版本相反的稿子，且没有任何提示。

表头字段同理：改掉 `job.title` 之后重跑，`llm_cache` 仍是 1 行（key 没变）。

## 四、一个方法论上的记录（写给我自己）

**我第一版对 #55 的判据是错的，而且错得很隐蔽。**

我最初用"模型被调用了几次"当判据，得到"第二次确实重新调用了模型"的结论 —— 与缓存行数的观测**互相矛盾**。
停下来写探针才发现两件事：

1. `generate_greeting` 在闸门不过时会做**修复调用**（提示词里带 `</previous>`），
   所以**一次调用本来就可能调两次模型** —— 我拿它当判据，等于用一个我自己没搞懂的指标去证明一个语义性质。
2. 我的第一版"过闸门"的回复**短了 1 个字**（79 不在 80-150），于是走了模板降级；
   而模板本身**是随 `variant` 变的**，所以"两次文本不同"这个断言被我自己的模板撑住了 —— 一个假的通过。

换成 `llm_cache` 的**行数**才站得住：`cache_key` 是那张表的主键，行数不涨就是 key 没变。

> 这已经是第四次同类教训（前三次：合规守卫按裸方法名误报、`.post` 命中自己的 fixture URL、
> 隐私扫描器自己携带隐私）。**共同点始终是：用一个粗粒度的观测量去证明一个精确的性质。**
> 这次的补丁是：先问"这个观测量的语义边界在哪、什么情况下它会骗我"，再去写断言。
