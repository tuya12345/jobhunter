## 三、两处做得比要求更好

### 1. 页面的写路径**主动**落实了 #57 的教训

规格只要求"第二次要如实说明是更新"。实际实现把**每一次**都说得清清楚楚，实测：

```
① 第一次  → created=true,  "已记入投递看板：新建记录 #1（线索「星澜科技」，渠道 官网，状态 applied）"
② 同一条再点 → created=false, "没有变化：记录 #1 已经是（渠道 官网，状态 applied）—— 重复点不会多记一次"
③ 换另一条线索挂同一岗位 → created=false,
     "更新了已有记录 #1：渠道 官网 → 内推"   channel_before='官网' channel_changed=true
```

`applications` 表全程只有 **1 行**（幂等成立）。

**为什么这条值得单独说**：#57 是在**采集端**（另一个仓库）发现的缺陷，
而消费端是**另一份代码**。开发会话没有等我提，就把它当成了通用教训用上了 ——
这正是从"改一个 bug"到"消除一类 bug"的差别。

### 2. 快照的 pydantic 模型用了 `extra="forbid"`

规格只警告"多字段可能让整批导入失败"。实现直接**拒绝**未知字段，
并在注释里写明理由：宁可报错让两边对齐契约，也不要"默默忽略一个字段"——那正是契约漂移的开始。

（代价是加字段必须先升 `schema_version`。这是**对的取舍**，因为契约就是为演进准备了版本号。）

## 四、新发现：#60（库版本落后时给的是堆栈 / 一串 500）

**这是我在你的真实库上撞到的**，根因不在 P7。

**事实**：你的 `data/jobhunter.db` 停在迁移 **`0001`**（项目现在是 `0005`），
里面有 1 份简历、1 个岗位。在这个库上：

- `jh leads import ... --dry-run` → 渲染出一个 **SQLAlchemy Traceback 面板**
- `jh leads serve` → 页面能开，但 `/api/leads` **HTTP 500**

**根因**：`storage/db.py` 的 `database_ready()` 只问"**表在不在**"：

```python
return "resumes" in set(sa_inspect(engine).get_table_names())
```

而 `cli/common.py` 的 `require_db()` docstring 恰好写着它要防的就是这件事：

> SQLAlchemy 在表不存在时报的是 `no such table: jobs` —— 对用户来说完全不知道该怎么办。
> 这里换成一句"请先运行 jh init"。

**它只覆盖了"表不存在"，没覆盖"列不存在（库版本落后）"** ——
库由 0001 建出来时 `resumes` 就在，关卡放行，然后在第一句 SQL 上炸掉。

`leads_cmd.py:153` 的注释也写着「先确认库在（**否则页面一起来就是一串 500**）」，
可它调的正是这个只检查表存在性的函数 —— **预料到了后果，但判据没覆盖到它**。

> 这个形态与 **#56**（`DELIMITED_TAGS` 只守"登记了的都生效"、守不住"该登记的没登记"）
> 是同一个：**守卫只覆盖了它被写出来时的那一个方向。**

**影响面不止 P7**：`jh cache stats` 需要 0004，在一个 0003 的库上会撞同样的墙。
而你的库停在 0001 已经很久了，期间没人发现 —— **因为用到的功能恰好不需要新列**。
这正是最该修的那类问题：**它不报错，直到某个新功能需要它。**

**修复方向**：把判据扩成"表在不在 **且** 迁移版本是不是 head"，
两条都不过就给同一句可操作提示。注意 **旧 < 新**（要升级）与 **旧 > 新**（装了个老版本）
是两件事，提示语该不一样。`jh init` 本身已经能升级（`init_cmd.py:82` 跑 `upgrade_head`），
所以这不是能力缺失，是**没告诉用户该去用那个能力**。

## 五、我自己在这轮犯的错（如实记录）

1. **三个 API 名靠记忆猜**（`ImportReport.created` / `Reachability.detail` / `LeadSnapshot.schema`），
   实际是 `added` / `reason` / `schema_`（`schema` 是 pydantic 保留名）。
   → 教训没变：**先查签名再写断言**。
2. **一次严重误报**：我写的一个检查脚本无条件给任何含 `KEY` 的字段打"已设置"标签，
   于是我一度以为 **`.env.example` 里泄露了真实 API Key**。
   核实后：那行是**空的**（我脚本的标签逻辑写错了）。
   → **如果我没核实就报出去，这会是一条"仓库泄露密钥"的假警报** ——
   而假警报的代价是别人开始不信你的警报。
