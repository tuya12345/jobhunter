# 线索快照契约（采集端 `leadhunter` →→ 消费端 `jobhunter`）

> **这是两个仓库之间唯一的接口。**
> 需求侧描述见 `docs/P7-消费端规格.md` §4（验证会话整理）；**这份文件是开发侧按实现
> 写下的权威版本** —— 字段名、类型、校验规则、空值语义都以它为准。
> 真实样例：`docs/leads-snapshot-sample.json`（从采集端真实库导出，公司名全部虚构）。
>
> 改了这份契约就要**同时**改采集端的导出（`lh leads export --format json`）。
> 单方面改字段名会让两边静默错位 —— 所以导入侧对**不认识的字段直接报错**，不静默忽略。

---

## 1. 顶层结构

```json
{
  "schema": "jobhunter.leads",
  "schema_version": 1,
  "exported_at": "2026-09-19T18:47:00+08:00",
  "generator": { "tool": "leadhunter", "version": "0.1.0" },
  "leads": [ /* 见第 2 节 */ ]
}
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `schema` | ✅ | **必须**等于 `jobhunter.leads`。不是它 → 报错"这不是本工具认识的快照" |
| `schema_version` | ✅ | 当前只认 `1`。**不认识就报错**，不"尽力而为地猜"（猜错的后果是字段错位入库） |
| `exported_at` | ➖ | 导出时间（ISO 8601 带时区）。仅记录，不参与任何判定 |
| `generator` | ➖ | `{tool, version}`，便于排障时知道是哪一版采集端导的 |
| `leads` | ✅ | 数组。**空数组合法**（表示"这次没采到"），导入会正常报"共 0 条" |

顶层与每条线索都**禁止未知字段**（pydantic `extra="forbid"`）：
采集端将来加了字段而消费端不认识时，**导入直接失败并指出是哪个字段** ——
这比"静默忽略一个字段、然后两边数据慢慢对不上"要好得多。

## 2. 一条线索（`leads[]` 的元素）

| 字段 | 类型 | 说明 |
|---|---|---|
| `external_id` | int \| str \| null | 采集端那条线索的 id。★ **只做溯源**，绝不当唯一键：采集端换台机器 id 就变了。入库统一存成字符串 |
| `name` | string（非空白） | 公司名。**匹配键**由它算出（见第 4 节） |
| `official_url` | string \| null | 官网招聘页 URL；可达性检查的对象 |
| `source_platform` | string \| null | 从哪看到的：贴吧 / 小黑盒 / 小红书 / 知乎 / 微信公众号 |
| `source_type` | `官网` \| `内推` \| `HR直招` \| null | 决定"该怎么投"，页面按它分组，也会成为投递记录的 `channel` |
| `evidence_text` | string \| null | **原始那句话**（"在哪看到的、原话是什么"）。线索可能是错的，留原文才能回头核对 |
| `evidence_url` | string \| null | 原始出处链接（截图帖、帖子 URL） |
| `note` | string \| null | 采集端整理的备注（可能含邮箱/微信，属于私密内容） |
| `http_status` | int \| null | 可达性检查的状态码（`0–599`）。★ **null = 未检查**，见第 3 节 |
| `checked_at` | string \| null | 那次检查的时间（ISO 8601 **带时区**） |
| `collected_at` | string \| null | 采集端**采集到**它的时间（与本库的 `created_at` 不同：后者是导入时间） |

### 时间格式（硬要求）

- 一律 **ISO 8601 且带时区**（`2026-09-19T18:47:00+08:00` 或 `…+00:00`）。
- **不带时区的时间会被拒绝**，并给出正确写法。原因：猜时区是最糟的一种"友好"——
  猜错 8 小时，"什么时候检查的"就永远是错的，而且没人会发现。
- 入库一律 **UTC**（本仓库全项目一致）；导入环节**不做本地化转换**（不做无谓的换算）。

## 3. `http_status` 的三种状态（"未检查" ≠ "失效"）

```text
http_status 有值且 200–399   → 已检查：可达
http_status 有值且 ≥ 400     → 已检查：HTTP nnn（入口可能已失效）
http_status 为 null          → 未检查
                              ├─ official_url 为 null → 「没有官网网址，无法检查」
                              └─ official_url 有值     → 「有网址，但当时没检查（网络不通或没跑检查）」
```

★ 后两种在页面上必须**分得清**，而且都**不能**显示成"失效"：
把"没检查"说成"失效"，用户会去放弃一条其实还能投的线索。

## 4. 导入的匹配规则（幂等靠它）

- 匹配键 = **公司名去掉所有空白**后的字符串（`jh leads import` 里叫 `name_norm`）。
  - 与采集端内部的合并规则**一字不差**（它也是 `"".join(name.split())`）。
  - 例：`云枢智能` 与 `云枢 智能` → 同一条（合并）；`星澜科技` 与 `星澜科技有限公司` → **两条**
    （采集端也不合并它们；消费端刻意不"更聪明"，否则会把生产者分开的两家公司并成一条 → 丢线索）。
  - 大小写敏感，同样与采集端一致。
- 这个键在库里是 **UNIQUE 索引**（迁移 `0005`）：重复导入在数据库层就插不进去第二行。
- 同一份快照里出现两次同公司 → 以**最后一条**为准，并在输出里报"合并同文件重复 N 条"。

## 5. 同一份快照导两次会怎样（幂等）

```text
第一次：新增 4 条、更新 0 条
第二次：新增 0 条、更新 4 条（其中 0 条内容有变化）   ← 库里行数不变
```

- "更新"= 命中了已有公司；"其中 N 条内容有变化"= 字段值真的不同。
- `jh leads import --dry-run` 只报数、**一个字都不写库**（连 UPDATE 都不发）。
- 快照里**出现**的字段以快照为准（`null` 就是 `null`）；**没出现**的字段不动本地的值。
  契约规定导出会带全部字段，所以"出现 null"与"字段缺失"的差别是有意义的。

## 6. 坏输入的错误提示（都指到"哪里不对、怎么改"）

| 情况 | 提示要点 |
|---|---|
| 文件不存在 | 给出路径 + 该目录下的 json 文件列表 + "采集端导出的是 .json" |
| 不是 JSON | 指出**第几行第几列**、文件开头长什么样、是不是把 HTML/登录页当快照了 |
| 不是 UTF-8 | 提示"另存为 UTF-8"（常见于被记事本/Excel 改过） |
| 空文件 | 提示"导出那一步是不是失败了" |
| `schema` 不对 | 提示"是不是把别的 JSON 当成线索快照导进来了" |
| `schema_version` 不认识 | 提示"采集端可能比本仓库新，请一起升级"，**不猜** |
| `leads` 不是数组 | 明确说"空数组是合法的，对象不是" |
| 字段类型/取值不对 | 指出**第几条线索、哪家公司、哪个字段**，不是一串下标 |
| 多出未知字段 | 指出字段名，提示"发现契约差异请写进交付声明，不要单方面改字段名" |
