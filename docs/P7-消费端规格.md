## 一、架构变了：P7 拆成"采集端"和"消费端"

```
┌─ 采集端（独立部署，不在本仓库）──────────────┐
│  D:\...\projects\leadhunter   （命令 lh）    │
│  lh leads add / list / export / apply        │
│  lh leads probe / capture（模拟器，只读）    │
│  → 产出线索，导出成 JSON 快照                │
└──────────────────┬───────────────────────────┘
                   │  用户手动"上传"（拷文件）
                   ▼
┌─ 消费端（本仓库 jobhunter）──────────────────┐
│  jh leads import <file.json>   → companies 表 │
│  jh leads serve                → 本地页面     │
│  页面：看线索 + 标记投递（读库）              │
└──────────────────────────────────────────────┘
```

**为什么这么拆**：采集端要装模拟器依赖、要连安卓设备、要在本机跑；消费端只要一个库和一张网页。
把两者混在一个仓库里，等于让"看线索"这件事也背上 `uiautomator2` 那套环境负担。

**所以本仓库里的 P7 范围是**：`companies` 表 + 导入命令 + 页面。
**采集类命令（add/probe/capture/export）不再在本仓库实现** —— 它们已经在 leadhunter 里了。

## 三、必须做的事

### 1. 数据库：加两列（**注意迁移号撞车**）

`companies` 表当前只有：
`id / name / official_url / source_platform / source_type / evidence_text / evidence_url / verified / note / created_at`

要加（采集端会带过来）：
- `http_status`（int，可空）—— URL 可达性检查的状态码
- `checked_at`（datetime，可空，UTC）—— 什么时候检查的

> ⚠️ **迁移号必须新建一个 `0005_*`，绝不能叫 `0004_*`。**
> 本仓库的 `0004` 已经是 `llm_cache_hits`（ISSUE #25）；而 P7 独立副本里也有一道
> `0004_company_http_status` —— **两个不同的 0004**，直接搬过来会撞车。
> 两边都已经各自跑过自己的 0004（`alembic_version` 里都写着 0004），所以只能新增。

**另外建议加一列做溯源**（不是必须，你判断）：
- `external_id`（String，可空）+ 索引 —— 记采集端那条线索的 id，用来回答"这条是从哪次导出进来的"

### 2. `jh leads import <file> [--dry-run]`

- 读 JSON 快照 → **pydantic 校验**（schema 见第四节）→ 入库 `companies`
- **幂等是硬要求**：同一份文件导两次，必须是「新增 0 条、更新 N 条」，**不是**变成两份
  - 匹配口径：**公司名归一化**（与采集端内部的合并口径一致，复用现成的归一化函数）
  - `external_id` 只做溯源，**不要**拿它当唯一键（采集端换一台机器 id 就会变）
- **`--dry-run` 一个字都不写库**（与 `jh job add --dry-run` 同一条纪律）
- 输出要**如实报数**：新增几条、更新几条、跳过了几条（格式参考 `leads add` 的
  「✓ 整理完成：新增 4 条、更新 0 条」）—— **不许静默覆盖**（这是本项目反复强调的纪律）
- 坏输入（不是 JSON / schema 版本不认识 / 字段类型不对 / 文件不存在 / 非 UTF-8）
  → **中文可操作提示**，不要裸 `JSONDecodeError` / `KeyError`

### 3. `jh leads serve [--port] [--host]`

- 起 FastAPI，**复用现有 services**（不重写业务）
- **必须默认绑定 `127.0.0.1`，不能是 `0.0.0.0`**
  —— 这是本地隐私工具，绑到 `0.0.0.0` 会让同局域网的人看到你的线索和简历信息
- 端口**不要用 8765**（StageBoard 占着），建议 `8787`
- 前端构建产物不存在时，给**可操作提示**（"先跑 `npm ci && npm run build`"），不要白屏

### 4. 页面（React/Vite）

必须有的：
- **线索列表**：按 `source_type`（官网 / 内推 / HR直招 / 未分类）分组
- 每条显示：公司名、投递方式、来源平台、**可达性**、官网链接、备注、**原始那句话**
- **可达性要区分三态**：「404 / 可达」「未检查（没有网址或当时网络不通）」——
  **"未检查" ≠ "失效"**，这条在采集端已经确立了，页面不能把它合并成一个"失效"
- **标记投递**：点一下把这条线索记成一次投递

**标记投递这条必须遵守的三件事**（这是本次最容易做错的地方）：

1. **复用 `apply_svc.set_status`**，不要另写一套写库逻辑。
   本项目已经因为"同一份数据两个写入口、口径不一致"吃过两次亏（#49 两个入口给出相反建议、
   #57 `leads apply` 静默改写渠道）。
2. **幂等**：重复点不会产生第二条记录。
3. **如实反馈**：如果这次是**更新**了已有记录（比如渠道从官网改成内推），
   页面上必须**说出来**，不能看起来和第一次一模一样 —— 这正是 #57 的原症状。

### 5. 文档

### 6. CI

  但 **API 层要有测试**（FastAPI 的 `TestClient` 就够）

## 四、JSON 快照契约（**这是两个仓库之间的接口，请以它为准**）

```json
{
  "schema": "jobhunter.leads",
  "schema_version": 1,
  "exported_at": "2026-09-19T18:47:00+08:00",
  "generator": { "tool": "leadhunter", "version": "0.1.0" },
  "leads": [
    {
      "external_id": 1,
      "name": "星澜科技",
      "official_url": "https://example.com/xinglan",
      "source_platform": "小红书",
      "source_type": "官网",
      "evidence_text": "刷小红书看到「星澜科技」在招 AI Agent 方向，官网投递 https://example.com/xinglan",
      "evidence_url": null,
      "note": "AI Agent 方向",
      "http_status": 404,
      "checked_at": "2026-09-19T18:47:00+08:00",
      "collected_at": "2026-09-19T18:47:00+08:00"
    }
  ]
}
```

约定：
- `schema` / `schema_version` **必填**。版本不认识 → **明确报错**，不要"尽力而为地猜"。
- `source_type` 只允许 `官网` / `内推` / `HR直招` / `null`（与采集端一致）
- `http_status` / `checked_at` 可空 —— **空表示"未检查"，不是"失效"**（第三节第 4 条）
- 时间一律 **ISO 8601 带时区**
- `leads` 是数组，空数组是合法的（表示"这次没采到"）

> ★ **采集端侧的配套改动不在本仓库范围内**（`lh leads export --format json` 由 P7 副本那边做），
> 但契约是**共同的**：如果你在实现时发现这个 schema 有问题（少字段、类型不对），
> **请写进交付声明**，由验证会话去和采集端对齐。**不要单方面改字段名。**

### ★ 契约的可执行参照物：`docs/leads-snapshot-sample.json`

上面那段是**说明**，真正用来对账的是这个文件 —— 它是**从采集端真实数据库导出**的
4 条线索（公司名全部虚构），字段、类型、空值语义、时区格式全部符合本契约。

**你可以现在就开工，不用等采集端**：把它当 fixture 写解析与测试即可。

它里面有两个**故意留下的测试点**：

| 线索 | 特点 | 要验什么 |
|---|---|---|
| `#1 星澜科技` | `http_status: 404` + `checked_at` 有值 | "检查过、入口可能失效" |
| `#2 云枢智能` / `#3 明澈数据` | `official_url: null` → `http_status: null` | "**没有网址**所以没检查" |
| `#4 虚构网络` | **有** `official_url`，但 `http_status: null` | "**有网址但网络不通**所以没检查" |

**#2/#3 与 #4 的区别是关键** —— 两者都不能显示成"失效"。
另外注意时间已经是 **UTC + `+00:00`**：导入时存库也一律 UTC，**不要在导入环节做本地化转换**。

## 五、红线（破一条整个阶段不算通过）

1. **页面不做自动投递** —— 用户点一下才记一次，绝无批量、绝无自动。
2. **页面不新增/删除线索** —— 线索的来源是导入，页面只读（+ 标记投递这一个写动作）。
3. `jh leads serve` **默认只绑 `127.0.0.1`**。
4. 导入**绝不静默覆盖**已有线索（要报数）。
5. 不把采集类命令（`probe`/`capture`）搬回本仓库 —— 它们要模拟器依赖。

## 六、验收方式（提前告诉你）

| 会怎么验 | 具体 |
|---|---|
| **导入幂等** | 同一份 JSON 连导两次，第二次必须是「新增 0 条、更新 N 条」，且库里行数不变 |
| **`--dry-run`** | **去数库里行数**，不看你的输出文案 |
| **坏 JSON** | 喂 5 种坏输入（非 JSON / 版本号 99 / `leads` 不是数组 / 字段类型错 / 空文件），都要中文可读错误 |
| **未检查 ≠ 失效** | 造一条 `http_status=null` 的线索，确认页面显示的是"未检查"而不是"失效" |
| **绑定地址** | 实际起服务，确认监听的**不是** `0.0.0.0` |
| **标记投递幂等** | 同一条线索点两次，`applications` 只能有一行；**第二次必须如实说明是更新** |
| **迁移链** | 从**空库**跑 `jh init`，确认能建到最新的 `0005`（不只是你本地能跑） |
| **CI** | Node 步骤真的在；`dist/` 没进仓库 |
